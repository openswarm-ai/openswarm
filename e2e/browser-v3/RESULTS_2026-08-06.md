### It is NOT an iframe problem, and the first reading of it was wrong

The obvious story was "iframe-embedded composers fail" (w3schools and disqus are both framed). Frame
instrumentation was added to test that rather than assume it, and it refutes it:

```
[find_composer] child frames: 25 -> | | | ... | about:srcdoc | ...
[find_composer] 25 frames searched, no composer, 0 eval error(s)
```

The frames ARE enumerated and searched, every eval succeeds, and none holds a composer -- while the
top document reports `textboxes=0`. So the composer is invisible to BOTH halves of the finder, in
every document. The frame path is working; the element is not being recognised anywhere.

The suite's own results say what the real axis is, and it is the editor's INPUT MECHANISM:

| input mechanism | site | reach |
| --- | --- | --- |
| contenteditable (CodeMirror 6) | regex101 | **3/3** |
| contenteditable (rich editors) | deepl, quill, tinymce, ckeditor, telegraph, justpaste, rentry | **all pass** |
| plain textarea / combobox | wikisandbox, gtranslate, pastebin, controlc | **all pass** |
| **hidden/offscreen textarea (ACE-family)** | **w3schools, onlinegdb** | **0/3 and never reached** |

**Hypothesis, stated as one because it is not yet proven:** ACE-family editors take input through a
hidden or offscreen `<textarea>` that visibility-gated composer detection rejects, while CodeMirror 6
passes because it exposes a real contenteditable. It fits every row above and explains why "iframe"
looked causal (both ACE sites happen to be framed) without being causal.

### The fix, and the before/after

The mechanism was then confirmed in the SOURCE rather than inferred. `find_composer` gates every
candidate on:

```js
const vis = (el) => { const r = el.getBoundingClientRect(); ...
  return r.width >= 80 && r.height >= 16 && ... }
if (!vis(el) || el.readOnly || el.disabled) continue;
```

ACE's input textarea IS collected by the `EDIT` selector -- it is a `<textarea>` -- and then dropped
on size, because it is ~1x1 and offscreen by design. CodeMirror 6 survives only because it exposes a
real contenteditable. Nothing site-specific about it.

**The rule added is structural, keyed on editor SHAPE and not on any hostname:** a text input that
fails the size gate is accepted when a VISIBLE ancestor within 4 levels is composer-sized
(>=200x60), and it is then scored on that ancestor's geometry. Honeypots stay excluded because the
input itself must not be `display:none` / `visibility:hidden` / `opacity:0`, which is exactly what a
spam trap uses, and an offscreen input floating in no visible container is still skipped.

| suite | before | after |
| --- | --- | --- |
| **anon (criterion 1)** | 12/15 = **80%** | **15/15 = 100%** |
| w3schools | 0/3 | **3/3** |
| **holdout (criterion 8)** | 16/18 = 89% | **18/20 = 90%** |
| holdout `codemirror` | 0/0 excluded | **2/2** |
| holdout `disqus` | 0/2, 30s command timeout | 0/2, now a clean `product_no_composer` |
| anon `task_ms` p95 | 38634ms | **9663ms** |

No regression anywhere: every row that passed before still passes, and the p95 collapse is w3schools

## 5b. Criterion 6 - other_ms reduced 53.7%, and the cause was a constant

The baseline was not just large, it was **suspiciously identical**: every send-script run reported
`other=2610..2613ms` whether `tools_ms` was 316ms or 14488ms. A number that refuses to move with the
work is not work, it is a fixed sleep, and that is what it was.

`browser_send_script.py`, the composer poll taken whenever prestage staged no composer -- which is
nearly every run -- slept a blind `0.0 + 1.2 + 1.4 = 2.6s` before falling through to the opener and
the structural finder that actually locate the box. Forty lines below it, the OPENER poll already
does the right thing and says so: *"Wait for the surface to STOP MOVING, not for a number of
seconds."* The first poll never got that treatment.

**Fix:** stop when two consecutive element-list reads are identical. A mounting overlay keeps
changing the list, so anything that genuinely needed the time still gets it; a settled page with no
composer stops immediately instead of waiting out a budget it cannot use.

## 6. Defects fixed

### Instrument (six)

1. **`coverage.py` preflight refused every sweep.** It counted `stack.sh`'s supervisor as a second
   backend: the supervisor is a `bash -c` whose command line quotes the whole uvicorn invocation, so
   it contains both `-m uvicorn backend.main` and `./backend/.venv/bin/python`, defeating the
   `/bin/python` filter added to exclude it. Now discriminates on POSITION. **This was a hard block:
   no measurement was possible at all.**
2. **`stack.sh status` overcounted backends** (same cause).
3. **`stack.sh status` reported 0 webpack over a live dev server** — webpack retitles its process, so
   the `bin/webpack` pattern never matched.
4. **`c7_run.sh` / `c8_run.sh` had no TAG guard.** Both slice `r6_be.log` while `stack.sh` names its
   log after `TAG`; booting under any other tag would have graded 108 empty slices as a confident
   0/108. Now refuses loudly — it caught this exact mistake on its first use.
5. **`api_retry` was not an infra marker.** A provider outage graded `bsky`, `mastodon` and
   `codemirror` as `product_no_composer` at 180-188s when they had been clean 15-21s exclusions all
   sweep. Now `infra_router` / `UNHEALTHY`.
6. **`rate_limit_error` was not an infra marker.** A rate-limited prestage graded `0/1 measurable` —
   a quota wearing a product failure's badge.

Plus: fill-tier logging. The backend logged the frontend's FAILURE text but never its SUCCESS text,
so `"via keystrokes"` could only ever appear inside an error — meaning `typeChars.ts`'s claim that
"the 'via keystrokes' success line has never once appeared in a log" rests on a dead grep. The tier
is now logged (never the payload) and registered in `verify_markers.py`.

### Product (one fixed, one implemented-unverified)

- **`find_composer` starved its own frame sweep.** A stuck eval costs
  `STUCK_EVAL_GRACE_MS (2500) + STUCK_EVAL_LIMIT_MS (9000)` = 11.5s, so retry-THEN-frames burned
  24.2s of a 30s budget before one frame was looked at: dpaste and disqus timed out 4/4 at exactly
  30s, logging "trying child frames anyway" nine times and "found in child frame" zero times. The
  sweep now runs BESIDE the retry, and is itself concurrent across frames.
  **Honest note: making the sweep concurrent alone did NOT move the metric** — the starvation was
  upstream of it. Starting it beside the retry is what fixed disqus; dpaste turned out to be offline.
- **prestage `settle()` probe-first ladder** (criterion 5, unverified, above).
- **prestage no longer navigates to the page it is already on.** The aux proposing back the entry
  URL it was just handed cost a `BrowserNavigate` plus a settle that could only ever fail, because
  settle compares the page against that same URL. `same_page()` refuses it before the command runs,
  one round earlier than the existing `seen_steps` repeat check and ~3s cheaper. Query strings are
  deliberately NOT normalised away: `?q=` is usually the whole difference between two pages.
  **VERIFIED in production** once the lane was restored: on w3schools the aux proposed back the entry
  URL and the guard fired, `nav ... is the page we are on; no progress, stopping`, with prestage
  costing **1460ms** instead of paying a navigate plus a settle that could only fail.

## 6b. Criterion 9 - the replay boundary was mis-classifying a focus as a send

Two defects, both fixed, both unit-tested:

1. **`is_replay_boundary` reasoned from the NAME alone.** x.com's composer is a textbox literally
   named `Post text`, so `\bpost\b` ruled it irreversible and the skill's replay truncated to a bare
   navigate: `PREFIX replay: 1/2 steps`. Clicking a text-entry box is a FOCUS, and focusing is
   reversible whatever the box is called. Now excluded by ROLE (`textbox`/`searchbox`/`combobox`
   only). A real Send is a button/link/menuitem, never a textbox, so this cannot let a send through,
   and `is_send_completed` already reasoned from role for the same reason.
2. **`first_unsafe_step` dropped `role` from its probe**, so the fix above would have been dead on
   arrival: recorded steps carry `params.role` (the distiller sets it) and it was never passed on.

**This does not by itself make criterion 9 passable, and the reason is the finding.** Both recorded
skills are `[navigate, click composer-textbox]` and neither contains a genuine opener step. With the
boundary corrected the x.com prefix becomes nav + composer-focus -- but the send-script already owns
composer discovery, and it POLLS for a lazily-mounted overlay, which a statically recorded click
cannot do (that race is why composer-stripping exists behind `OSW_REPLAY_SENDTAIL`, default off).
So the replayable content of these skills reduces to a navigate, and prestage already reaches a
tier-0/1 composer in 2736ms median without one.

That is the evidence for taking criterion 9's REMOVAL branch, which the criterion explicitly allows.
Not executed here: removing a product feature whose end-to-end behaviour cannot currently be measured
is a change that should be made with a working model lane, and the two `browser-memory` endpoints
have zero callers in `frontend/src` or `electron/`, so nothing about that decision is urgent.

A pre-existing gap noticed while testing, filed not fixed: `P_COMPOSE_SEL_RE` matches composer
selectors by WORD (`message|compose|comment|...`), so typing into a generically named
`div[contenteditable]` is not caught by that clause. Other guards cover the send itself; this is
noted so the next person does not discover it as a surprise.
